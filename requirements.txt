# MFSTNet — pinned dependencies (NFR-08: clean-machine reproduction)
#
# Versions are PINNED, not ranged. A range that resolves differently in
# November than it did in August breaks reproducibility silently.
#
# Every version below is the one this environment actually runs, read from the
# installed distributions rather than chosen by hand. That is the point: a pin
# nobody has run is a guess, and until 2026-08-20 this file was full of them —
# 21 of 35 lines were ranges despite the paragraph above, and not one of the
# seven pinned-and-installed packages matched its pin (stable-baselines3
# declared ==2.3.2 against 2.9.0 installed; SUMO ==1.19.0 against 1.27.1).
#
# When anyone adds a dependency, they add the pinned line in the SAME commit.
#
# Audited 2026-08-18 by walking the AST of every source file and comparing the
# imports against this file, in BOTH directions. Re-audited 2026-08-20 against
# the installed environment, which is the direction the first audit missed.
# tests/test_requirements_complete.py runs both.

# ---- PyTorch: install FIRST, from the CUDA index ----
#
#   pip install torch==2.13.0+cu126 torchvision==0.28.0+cu126 \
#       --index-url https://download.pytorch.org/whl/cu126
#   pip install -r requirements.txt
#
# Verify:  python -c "import torch; print(torch.cuda.is_available())"
#
# NOT pinned here: pinning a platform-index wheel in this file reintroduces the
# defect the separate install exists to avoid.
#
# **cu126, not cu121.** This instruction said cu121 until 2026-08-20, and that
# index no longer carries torch at ANY version — `pip index versions torch
# --index-url .../cu121` answers "No matching distribution found". Following the
# documented command therefore resolved to the CPU wheel without saying so,
# which is exactly how this machine ended up on torch 2.13.0+cpu with an idle
# RTX 4050.
#
# cu126 carries 2.13.0; cu128 stops at 2.11.0, so it would mean a downgrade.
# The GPU is compute capability 8.9 (Ada) on driver 610.62, which CUDA 12.6
# covers. Same version, same API, different compute backend — no code changes.
#
# On a machine with no NVIDIA GPU, use .../whl/cpu deliberately rather than by
# accident. Training works either way, but not equally: measured on a
# five-camera pilot and extrapolated to 359 sequences at 100 epochs, the full
# A-H ablation is ~3.8 h on this GPU against ~12.3 h on this CPU.
#
# The wheel alone was not enough. `train_mfstnet.py` had no device handling at
# all until P32 — no `.to()`, nothing — so a CUDA build changed precisely
# nothing and training stayed on the CPU while the GPU idled. If you are
# reading this because training feels slow, check BOTH: the build here, and
# that `--device` reports cuda when the run starts.
